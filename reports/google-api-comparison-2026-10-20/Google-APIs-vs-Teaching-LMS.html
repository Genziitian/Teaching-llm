Every one of the 316 directory API names has its own purpose, project fit, recommendation, effort estimate, cost considerations and source link below. Versions are listed under the same API to avoid pretending v1/v1beta are separate products. High-fit services receive deeper implementation comparisons. Most low-fit entries were assessed from the official directory metadata and the project's architecture, not by individually testing every API. A link is a reference, not proof of account eligibility or a working integration.

Evidence labels: “Existing” means a source integration was found; “Optional” means technically plausible with a specific product requirement; “Migration only” means replacing part of the current stack; “No current fit” means unrelated to the project's present needs, not technically impossible; “Avoid” includes verified retired services or unsuitable new-adoption paths. No production credentials, billing configuration, quotas or enabled-service inventory were inspected. Do not disable an existing service based only on this report.

What our project actually needs

Teaching LMS is an existing web and Flutter learning product: Google sign-in, role-based course access, paid offerings, protected lectures/documents, homework, community/support, live sessions, manager scheduling and notifications. The name “Teaching LLM” does not itself establish a need for a model-training platform.

The current Prisma schema uses PostgreSQL. The README still describes SQLite and older behavior, so the inspected application source takes precedence. Render configuration defines app build/start and an analytics schedule; this is configuration evidence, not confirmation of the live hosting state. Supabase clients in upload/download routes establish file-storage integration. Existing code also includes Agora live-class routes, Razorpay checkout, web Sentry/PostHog dependencies, Flutter Firebase Analytics, and SMTP/Apps Script email paths.

The critical product boundary is manager Sync publishes the day's sessions. Any future Calendar export, automatic Meet workflow or class reminder must preserve that approval boundary. Google APIs do not become the authority for course enrollment or paid access simply because they store a related resource.

Detailed comparisons for the decisions that matter

1. Google Identity Services and OAuth/OIDC

Current: Flutter uses google_sign_in; the backend exchanges/verifies the Google credential through Google's token-information endpoint, checks the audience and issues LMS session behavior. This is a Google sign-in integration, not proof of a Firebase Authentication deployment.

Use: Retain one mapped LMS account per intended Google identity and verify sign-in on the release app and website. Google login proves identity; it does not grant Calendar write access, private Drive access, Gmail access, a Workspace seat, course enrollment or a paid entitlement. Those require separate authorization and application checks. The directory's old oauth2 label must not be read as a recommendation to adopt deprecated endpoints.

Tradeoff and acceptance: Changing to Identity Platform/Firebase Authentication would require a real account/session migration, linking rules, revocation and existing-user testing. Keep the current architecture unless that migration solves a named problem. Check new/returning users, wrong client audience, terminated users, logout and account linking. Google Cloud API enablement alone will not fix sign-in.

2. Drive API versus Cloud Storage and Transcoder

Current: drive.ts resolves file IDs and fetches bytes as the service account, optionally a delegated Workspace administrator. It also has public/API-key fallback paths. The source explicitly notes that the student's Google identity is not the file-fetch identity. A student's ability to open a file in their own Drive therefore does not imply that the backend can retrieve it.

Use: Keep Drive for existing restricted materials where the server identity has legitimate access. Preserve LMS enrollment checks before serving bytes, and validate seeking/range requests and document exports. Google account sharing and LMS course access are separate boundaries. Broadening a file to “anyone with the link” is not equivalent to protected distribution.

Alternative: Cloud Storage can become an owned origin; Transcoder can produce playback renditions. Together they require upload paths, metadata, job state, access-scoped URLs or delivery, player support, storage and egress budgeting, content migration and rollback. Transcoder does not deliver DRM and Storage does not automatically check enrollment. Benchmark actual concurrency and origin failures before deciding to migrate. Neither merely enabling Drive nor moving objects proves that playback is reliable.

3. Admin SDK Directory versus Classroom, Groups Settings and Cloud Identity

Current: Enrollment/group synchronization uses delegated Workspace credentials and Directory group membership scopes. The project already queues membership work; this is a separate operation from creating a course or publishing a class.

Use: Retain Directory for ADD/REMOVE membership operations. A service account needs the intended Workspace administrator delegation, approved scopes and permissions; creating a Cloud service account alone is insufficient. Do not assume the institution controls arbitrary students' personal Gmail accounts. Removing an enrollment must reliably remove any corresponding group access according to our business rules.

Alternatives: Groups Settings changes group policies rather than membership. Cloud Identity serves different enterprise identity/group management needs. Classroom duplicates a separate course/assignment system and is useful only when a real Google Classroom workflow must integrate. Test retries, repeated enrollment requests, removals, Google rejection, domain restrictions and a queue worker restart before declaring sync reliable. This review did not execute those flows.

4. Sheets API versus PostgreSQL

Current: External enrollment calls appendEnrollmentToSheet, which writes an operational row and catches/logs errors. PostgreSQL models remain the durable source of application users, orders and enrollments.

Use: Keep Sheets as a convenience for authorized staff reporting if staff actually use it. Verify spreadsheet sharing to the service identity, row field mapping, spreadsheet/tab identifiers, quota handling and failure visibility. The row includes student contact/profile information, so access should match the operational purpose.

Limit: A missing or duplicate spreadsheet row must not silently create or cancel an LMS enrollment. Do not make Sheets a second authoritative database or describe it as a database backup. If reconciliation becomes important, record a stable enrollment reference and reconcile deliberately rather than adding repeated blind append retries. No spreadsheet contents or live row writes were inspected here.

5. FCM, FCM Data, Pub/Sub and notification publication

Current: Firebase Admin sends pushes and Flutter registers/handles messages. Source includes user notification preferences and course/topic subscriptions. Session publication and class-related notifications depend on manager Sync snapshots.

Use: FCM remains the device push channel; its core product is listed as no-cost in Firebase pricing. Hosting, queueing, logs or exports around it can still incur costs. FCM Data can help investigate aggregate delivery trends but is not an individual guaranteed-read receipt. Pub/Sub is a backend event bus, not the student push display service.

Acceptance: Confirm that a real device receives the intended message in foreground/background, handles token rotation and opt-out, routes to an authorized destination and receives no unpublished draft class notification. Retain an in-app notification record because push delivery should not be the only copy of an important schedule update. Test retries without duplicate user-visible messages. API configuration and source presence do not prove delivery.

6. Play Billing, Android Publisher, Reporting and Integrity

Current: Flutter uses in_app_purchase; the notes verification route calls a shared helper that queries purchases.products.get for com.teaching.lms. Website commerce also has Razorpay flows.

Use: These serve different functions: Billing initiates the device purchase; Android Publisher supplies backend purchase state; Reporting reads app-quality information; Integrity supplies device/app risk signals. None is a substitute for the others. A Google Cloud service account also needs the intended Play Console access; Cloud IAM alone is not sufficient.

Acceptance: Validate the requested product and package, purchase state, token reuse/idempotency and correct LMS entitlement before granting access. Test pending, canceled, repeated, restored and refunded outcomes plus acknowledgement as applicable. The inspected helper verifies a one-time product; it is not proof of complete subscription lifecycle handling. Pub/Sub can be evaluated for relevant real-time developer notifications only after event handling and idempotency are designed. This report is not a checkout-policy audit and does not certify the existing purchase flow.

7. Calendar API versus our existing calendar

Current: Events and published daily session snapshots are stored in PostgreSQL. The inspected import/export routes implement JSON/CSV operations, not Google Calendar synchronization. Do not infer Calendar API integration from the presence of a calendar screen or a Meet URL.

Useful addition: Opt-in export of an approved live class to a student's calendar or an instructor-owned calendar. A downloadable calendar invite or explicit Add-to-Calendar link may satisfy a one-way reminder request with less account access than bidirectional synchronization.

If using the API: Choose a specific calendar owner and narrow scopes, store external event IDs, reconcile update/cancel/delete behavior, handle token revocation and prevent feedback loops. Drive notifications and Calendar invitations must not publish draft edits before manager Sync. Test IST boundaries and any explicit international time-zone requirement. No Google Calendar account or calendar permission was tested.

8. Meet API versus stored Meet links and Agora

Current: The LMS stores Meet links, while backend Agora live routes exist for token-based live-room behavior. The presence of Agora source does not establish complete Flutter live-call coverage.

Useful addition: Create meeting spaces or import authorized meeting records and eligible attendance/recording/transcript metadata. Google's current Meet documentation supports these administrative workflows, with access and Workspace capability constraints. For attendance, distinguish a conference participant from a verified LMS student; display-name matching is not reliable identity mapping.

Boundary: Meet REST is a meeting-management API, not a drop-in implementation of our branded Agora classroom. The Meet Media API/add-ons have their own access and product constraints and should not be assumed to provide a complete embedded classroom. Keep the existing provider unless a real class workflow warrants a scoped integration. Attendance corrections must be reviewable before affecting any important student outcome.

9. Workspace Events with Meet

Use: Subscribe to relevant Meet lifecycle or artifact-ready events if automatic post-class processing becomes a product need. The source currently has no demonstrated Workspace Events subscription pipeline.

What must be built: Authorized subscriptions, a supported delivery destination, renewals, verification, duplicate handling and a durable artifact-processing job. Process only events for eligible courses/teachers. A “conference ended” event does not mean every LMS student attended or that a transcript exists. Store provider IDs and provenance, and respect changed/deleted resource state. This is optional automation around Meet, not a prerequisite for a manually pasted meeting link.

10. Classroom versus our courses and homework

Use only for an actual partner workflow: Import a teacher's existing Classroom roster/coursework or link an institution's existing coursework. Google documents that personal accounts can use Classroom, while some administrator behavior requires Workspace for Education. API access is not automatic access to an institution's private classes.

Overlap: We already own course identity, enrollment, paid access, homework, feedback and progress. A second course system needs an explicit owner for each record type, mapping IDs, sync direction, conflict rules and deletion behavior. Do not migrate learners or allow a Classroom enrollment to silently grant paid LMS access. There is no present source evidence of a Classroom integration, so this is a conditional future bridge, not a necessary upgrade.

11. Gmail, SMTP and Apps Script

Current: The email service tries SMTP and then an Apps Script webhook. It can return a simulated result when neither sender is configured. That source path means an application success response alone is not proof of an inbox delivery.

Comparison: Gmail API could offer a scoped OAuth sender, but it still has Google account sending constraints and is not automatically a high-volume transactional email service. Apps Script API manages/executes script projects; calling an already deployed webhook is a different path and does not itself require the management API. Gmail Postmaster Tools reports reputation/delivery trends for eligible domain traffic; it sends no emails.

Recommendation: Verify the actual configured sender and real receipt for welcome, purchase and support messages before adopting a new sender. Prefer send-only permissions over mailbox reading. Do not replace all email paths merely because the library lists Gmail. Review queueing/retry/delivery evidence separately if volume or reliability becomes a measured issue.

12. Firebase Analytics and Google Analytics report APIs

Current: Flutter has Firebase Analytics and an Analytics navigation observer; the web package has PostHog and the app has its own analytics job. This is source evidence for several analytics paths, not confirmation that production dashboards contain correct data.

Comparison: Analytics SDK records events; Analytics Data reads reports; Analytics Admin configures properties. BigQuery is a possible future warehouse export, not a requirement for basic screen analytics. Tag Manager is another tag-management layer and should not create duplicate collection.

Recommendation: Define the actual decisions managers need: failed sign-ins, playback failures, course completion, purchase conversion or student support. Keep business counts from authoritative backend data. Minimize identifiers in analytics, check event naming and test representative journeys. Build a reporting API integration only if managers need those reports inside the LMS rather than the existing vendor console.

13. Crashlytics, Play Reporting, Performance and Test Lab

Gap: Firebase Core/Messaging/Analytics are installed, but no Flutter Crashlytics or Performance Monitoring dependency was found in the inspected package. Web Sentry is a separate path and should not be assumed to capture native Flutter crashes.

Best use: Start with Play Console Android vitals and a small real-device release check. Add Crashlytics SDK if device-crash visibility is a gap. Add Performance Monitoring if slow startup/network traces need evidence. Test Lab can broaden Android device coverage, with quotas or paid execution. The Crashlytics REST entry alone does not perform SDK instrumentation.

Acceptance: A controlled test error appears in the intended project and release, logs do not leak sensitive tokens, source/symbol information is usable and real flows can be reproduced. Testing login, downloads, playback and purchases needs appropriate test accounts and provider setup; an APK build passing is insufficient.

14. Play Integrity, App Check and reCAPTCHA

Use: Consider these for a measured abuse problem. Play Integrity provides Android risk signals, App Check attests supported clients/backends, and reCAPTCHA assesses selected web interactions. They address different attack surfaces.

Limits: The Next.js backend must verify and bind signals to the intended request; enrollment and role checks stay mandatory. Avoid blanket rejection of legitimate devices on one uncalibrated signal. Establish replay handling, expiry and an accessible recovery route. None provides DRM, screen-recording immunity or proof that a student personally watched a lecture. Existing rate limiting remains relevant even after one of these is added. No abuse volume or attestation was measured during this review.

15. Gemini Developer API versus the enterprise AI platform

Current: The inspected application source did not show a Gemini, OpenAI, Anthropic or Vertex inference caller. Existing prompt/feedback administration should not be assumed to be a working AI tutor.

Small useful pilot: Let a teacher generate a draft summary or practice question set from one authorized lesson. Keep original references, require review before publication and measure wrong answers and editing time. Course-grounded Q&A needs enrollment-filtered retrieval before the model sees content, citations, a useful “not enough information” response and safeguards against notes or chat instructions overriding permissions.

Comparison: Gemini Developer API is a simpler evaluation path for a small feature. The enterprise platform offers cloud-managed model/agent infrastructure and controls, with a larger setup surface; current naming in the directory and Console banner may differ from older “Vertex AI” tutorials. Neither requires us to train models or provision TPUs. Model quality, terms, region and quotas must be checked for the selected model rather than assumed from a product name.

Cost/data: Google lists different free/paid tier data-use treatment and token/tool rates; choose a suitable current contract before sending private learner information. Do not assume every paid or contributor variant has identical terms. Keep calls server-side, minimize personal data, cap input/output and per-user requests, and track actual cost. No particular model or monthly rupee amount is recommended without a workload.

16. Vision versus Document AI versus PDF text extraction

Use: OCR can convert scanned materials into searchable drafts. Vision supplies OCR/image analysis; Document AI adds processor-oriented structured document extraction. For a digital PDF that already contains selectable text, ordinary extraction may avoid a paid OCR call entirely.

Project fit: This LMS distributes lectures and notes; extraction is useful only if we intentionally build searchable content or teacher-authoring workflows. Do not import Quiz LAB requirements from another project as if they already exist here. Test real handwritten/printed examples, languages, equations and tables. Preserve source crops when diagrams cannot be represented accurately, and never silently invent an unreadable answer or figure.

Cost: Vision is feature/unit-based; Document AI is processor/page-oriented, with related object storage/processing costs. Benchmark a small representative batch and teacher correction time before choosing. An OCR response is not a verified academic answer key.

17. Speech, Translation, Text-to-Speech and Video Intelligence

Use: Speech can produce lecture transcripts, Translation can make content more accessible across languages, Text-to-Speech can create audio notes, and Video Intelligence can propose richer video annotations. These are independent metered capabilities; there is no need to enable all of them.

Smallest order: First confirm recording rights and a real learner need. If transcript search solves it, start there. Reuse the transcript for reviewed summaries or translation instead of repeatedly analyzing the whole video. Preserve timestamps and the original text, flag uncertain technical terms and allow correction. A transcript does not establish attendance, and translated equations/instructions require academic review. Storage, generation, processing and delivery costs are separate.

18. Cloud Tasks, Pub/Sub, Scheduler and Workflows

Current: Group sync has application/database queue logic; Render config declares a daily analytics schedule. Source configuration does not prove live job execution or restart safety.

Choice: Cloud Tasks suits a retryable HTTP job; Pub/Sub suits event fan-out; Scheduler supplies recurring triggers; Workflows suits a multi-stage orchestrated process. One task queue plus an authenticated handler may be enough if current jobs demonstrably lose work during restarts. Do not introduce all four merely to move one cron.

Acceptance: Jobs survive app restart, duplicate deliveries do not duplicate side effects, failures are visible and replayable, per-run batches are bounded and credentials stay server-side. Schedule handling must use the intended time zone and must not publish draft classes. Assess operational benefit against a separate Google dependency and metered usage.

19. Cloud Run, Cloud SQL and storage migrations

Use: These could provide an alternative hosting/database/file foundation, but they are migration projects rather than isolated feature integrations. Render memory or restart issues need measurements before concluding that another host fixes them. Existing PostgreSQL is not an outdated SQLite setup merely because the README says so.

Required comparison: Real memory/CPU and concurrency, long-lived SSE requests, cold starts, background workers, connection pooling, database backups/restore drills, file delivery, regional latency and total operational cost. Maintain a cutover and rollback plan and verify all authenticated flows. Do not simultaneously replace host, database, auth and files without an explicit migration objective; the source here does not establish such a need.

20. Search, Digital Asset Links and Maps

Search: Search Console helps observe public SEO; it does not reveal private lectures. Indexing API is restricted to eligible job/livestream structured data, so it is not a generic “index our courses” service. Custom Search JSON API is closed to new customers with a 1 January 2027 transition deadline for existing customers. Use normal site discoverability and an enrollment-filtered internal index for their respective needs.

Links: Digital Asset Links can check website/app association. The app still needs a correct publicly served HTTPS statement, Play signing fingerprint, manifest and destination handling. This review did not recheck the deployed association file; no prior endpoint status is presented as current.

Maps: The four visible screenshot cards—Android Maps, iOS Maps, JavaScript Maps and Roads—do not fill a current LMS gap. A future physical-center page might need a Maps link or embed. It would not justify road matching, geolocation, route optimization or environmental APIs. The individual directory and supplemental reviews below explain each capability separately.
